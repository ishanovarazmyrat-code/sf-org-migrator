What it does

Everything needed to lift records and their files out of one org and land them in another.

🗂️

Records and files together

Account, Contact, Opportunity and Case out of the box; custom objects with a little config. Files travel with the records they belong to.

📦

Large files

Files up to 2 GB each. Binaries stream to disk and upload in multipart chunks, so a big attachment never has to fit in memory.

🔁

Resumable

Every phase is re-runnable. Progress is tracked in a manifest, so a re-run picks up exactly where it stopped and retries only what failed.

🔗

Relationships preserved

File-to-record links are rebuilt in the target org, resolving each source record to its new target record through external-ID fields.

🕑

Version history (optional)

Migrate just the latest version of each file, or the full version history in order — your choice per run.

🔐

Passwordless login

Authorize each org once through an OAuth device flow. No passwords are stored, and it works the same on a laptop or an unattended VM.

🧭

Automatic field mapping

Copies the fields both orgs share and can write, maps record types by name, and handles state/country codes so inserts don't fail on mismatched values.

🖥️

Terminal or web UI

Drive it from the command line, or open a local web UI with buttons, a live log, and a progress bar. Same engine underneath.

How it works

Four steps, each resumable. Run them in order the first time; re-run any of them to retry.

Connect

Authorize the source and target orgs, then run a preflight check that tells you what's ready and what's missing.

Records

Copy the selected objects into the target, upserting on an external ID and re-pointing lookups to the migrated parents.

Files

Download every file from the source, upload it into the target, and rebuild the links back to the right records.

Verify

See the final counts — documents, versions, and links — plus any failures, so you know the migration is complete.

Quick start

Prepare the target org once, then run the tool.

1 · Install the package in your target org

One click adds the fields, classes, custom setting and permission set the migration needs:
Install into a Salesforce org →  then choose Install for All Users. For a sandbox, replace login with test in that URL.

Then assign yourself the permission set. Setup → Permission Sets → Migration Access → Manage Assignments. A newly installed field is invisible without it, and the migration will stop and say so rather than move nothing.

2 · Create an External Client App in each org

Once per org, so the tool can sign in without storing a password. Setup → App Manager → New External Client App:

  • Callback URL https://login.salesforce.com/services/oauth2/success (test instead of login for a sandbox)
  • Scopes: Manage user data via APIs (api) and Perform requests at any time (refresh_token, offline_access)
  • Then open the app → Settings → OAuth Settings → Edit → Enable Device Flow ✓ — easy to miss, and nothing works without it

Copy the Consumer Key from each org; step 3 asks for it. New apps take a few minutes to activate — if login says invalid device code straight away, wait and retry. Full walkthrough: OAUTH_SETUP.md.

3 · Run the tool

# needs Node.js 22 or newer
npm install -g sf-org-migrator

# state lives where you run it, like git — one folder per migration
mkdir my-migration && cd my-migration

sf-org-migrator login source   # paste that org's Consumer Key, then
sf-org-migrator login target   # approve the code in a browser
sf-org-migrator doctor         # preflight: what's ready, what's missing

# try a handful of files first
sf-org-migrator manifest --limit 3
sf-org-migrator migrate

# then the real thing
sf-org-migrator manifest --force
sf-org-migrator migrate        # records + files, end to end

Each login prints a URL and a code — open it in a browser signed into that org. Use an incognito window for the second one, or you will authorize the first org twice.

4 · When something goes wrong

sf-org-migrator verify     # where the run got to
sf-org-migrator failures   # what broke, grouped by cause

failures splits problems into worth retrying and needs a fix first, and prints the phases to re-run in the right order. Every rejected record also lands in a CSV under work/errors/ with its reason. Every phase is resumable — run the same command again and it continues.

Short on disk? Add --stream and each file goes straight from one org to the other without touching disk. The trade is that an interrupted transfer restarts that file instead of resuming it.

5 · Migrating a custom object

The packaged fields cover the standard objects. A custom object needs three things, and the second is the one people miss:

  1. An external Id field on the target — Legacy_<Object>_Id__c, Text(18), External Id, Unique.
  2. Field-level access to it. A newly created custom field is invisible to every profile until something grants it — literally invisible: it does not appear in the object's describe, so the tool cannot see it either. Put it in a permission set and assign that to whoever runs the migration. Skip this and the migration stops with a message naming the field.
  3. Its lookups mapped under parents. A lookup holds a record Id from the source org, which means nothing in the target. Listing it tells the tool what to re-point it at; leave it out and the field is dropped by design.
{
  "name": "Shipment__c",
  "externalId": "Legacy_Shipment_Id__c",
  "fields": "auto",
  "parents": { "Account__c": "Account" }
}

Add that to the objects array in migration.config.json, parents before children — the migration processes them in order.

Prefer buttons over the terminal? Start the local web UI — setup, object and field selection, and a live progress view:

sf-org-migrator ui   # then open http://localhost:4599
